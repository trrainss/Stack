# STACKLAB

Коммерческий сайт digital-студии с закрытой панелью управления: публичные страницы, работающая форма заявок, база данных, управление контентом и уведомления.

Проект собран на Next.js (App Router), TypeScript в строгом режиме, Tailwind CSS, Prisma и Zod. Локальная проверка выполнена на реальной базе SQLite; схема подготовлена к переключению на PostgreSQL для production.

## Что реализовано

**Публичная часть**

- `/` - главная: первый экран с интерактивной композицией интерфейсов, проекты, услуги, преимущества, этапы, блок о студии, отзывы (или честное пустое состояние), FAQ, финальный призыв.
- `/projects` и `/projects/[slug]` - сетка концептуальных кейсов и страница проекта с задачей, решением, технологиями и ссылкой на опубликованный сайт (если она указана).
- `/services` - услуги с составом работ, аудиторией, результатом, ориентировочной ценой и кнопкой заказа.
- `/about`, `/contacts`, `/privacy`, страница 404.
- Адаптивная шапка с полноценным мобильным меню (блокировка прокрутки, Escape, focus trap), подвал с настраиваемыми контактами.
- Анимации появления секций, hover-состояния, аккордеон FAQ, поддержка `prefers-reduced-motion`.
- SEO: уникальные title/description, canonical, Open Graph, JSON-LD (Organization, FAQPage, CreativeWork), `sitemap.xml`, `robots.txt`, favicon, `noindex` для `/admin` и API.

**Форма заявки**

- Поля: имя, контакт, способ связи, тип проекта, бюджет, комментарий, согласие с политикой.
- Клиентская и серверная валидация (Zod), honeypot, проверка времени заполнения, лимиты по IP и контакту, дедупликация повторных отправок.
- Реальное сохранение в базу, уникальный номер заявки, понятное подтверждение и сохранение введённых данных при ошибке.

**Админ-панель `/admin`**

- Вход по email и паролю, scrypt-хеширование, серверные сессии в базе, CSRF-токен, лимиты попыток входа, выход.
- Обзор: количество заявок по статусам, график за 14 дней, последние обращения, состояние уведомлений, быстрые действия.
- Заявки: поиск, фильтр по статусу, сортировка, пагинация, карточка заявки, смена статуса, внутренние заметки, копирование контакта, удаление с подтверждением, экспорт CSV.
- Проекты, услуги, FAQ, отзывы, этапы: создание, редактирование, публикация/снятие, сортировка, удаление.
- Главная страница: заголовки, подзаголовки, кнопки, пункты преимуществ, видимость блоков.
- Контакты: email, Telegram, TikTok, телефон, тексты страницы и подвала, валидация ссылок.
- Настройки: SEO, тексты страниц, политика конфиденциальности, включение каналов уведомлений.
- Загрузка обложек проектов с проверкой MIME по сигнатуре файла и ограничением 2 МБ.
- Все изменения публикуются на сайте сразу после сохранения (revalidate), без правки кода.

**Уведомления**

- Telegram (отдельный бот) и email (SMTP) включаются в настройках.
- Заявка сохраняется всегда, даже если канал недоступен. Каждая попытка пишется в журнал, отправку можно повторить из карточки заявки.

## Быстрый старт

```bash
npm install
```

Создайте `.env` на основе примера (Windows: `copy`, macOS/Linux: `cp`):

```bash
copy .env.example .env
```

Сгенерируйте секрет и заполните `AUTH_SECRET`:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

Локальная база уже настроена на SQLite (`DATABASE_URL="file:./dev.db"`). Примените миграции и заполните демо-контент:

```bash
npm run db:migrate
npm run db:seed
```

Создайте администратора. Укажите `ADMIN_EMAIL` и `ADMIN_PASSWORD` в `.env` (пароль не короче 12 символов). Если `ADMIN_PASSWORD` пустой, скрипт сгенерирует пароль и покажет его один раз:

```bash
npm run admin:create
```

Запустите разработку:

```bash
npm run dev
```

- Сайт: `http://localhost:3000`
- Панель: `http://localhost:3000/admin`

Публичной регистрации администраторов нет. Повторный запуск `npm run admin:create` обновляет пароль и отзывает все активные сессии.

| `TELEGRAM_CHAT_ID` | нет | Чат или канал для уведомлений |
| `EMAIL_SERVER_HOST` | нет | SMTP-хост |
| `EMAIL_SERVER_PORT` | нет | Порт SMTP (по умолчанию 587) |

## База данных

Модели: `AdminUser`, `AdminSession`, `Lead`, `NotificationLog`, `Project`, `Service`, `Testimonial`, `Faq`, `ProcessStep`, `SiteSetting`, `RateLimit`.

- Индексы: статус и дата заявки, контакт, тип проекта, публикация и сортировка контента, сессии по пользователю и сроку.
- `Lead.number` уникален; номер выделяется от текущего максимума с повтором при конфликте.
- Внутренние заметки хранятся в `Lead.internalNotes` и не выводятся на публичном сайте.
- Каскадное удаление применяется к сессиям и журналу уведомлений.

### Две схемы: SQLite и PostgreSQL

Prisma требует жёстко заданного провайдера в файле схемы, поэтому в проекте два файла с одинаковыми моделями:

| Файл | Провайдер | Где используется |
| --- | --- | --- |
| `prisma/schema.prisma` | SQLite | локальная разработка и тесты |
| `prisma/postgres/schema.prisma` | PostgreSQL | production (Vercel, VPS) |

`scripts/prisma-target.mjs` смотрит на протокол `DATABASE_URL` и запускает Prisma с нужной схемой. Модели в двух файлах обязаны совпадать — это проверяет юнит-тест, поэтому расхождение не пройдёт незамеченным.

Если меняете модели, обновите оба файла и создайте миграции для каждой схемы:

```bash
npm run db:migrate -- --name change_name                          # SQLite
$env:DATABASE_URL="postgresql://..." ; npm run db:migrate -- --name change_name   # PostgreSQL
```

Для PostgreSQL миграции можно сгенерировать и без живой базы (нужны обе переменные, иначе Prisma не разрешит `directUrl`):

```bash
$env:DATABASE_URL="postgresql://user:pass@localhost:5432/db"
$env:DIRECT_URL=$env:DATABASE_URL
npx prisma migrate diff --from-empty --to-schema-datamodel prisma/postgres/schema.prisma --script
```

## Заявки и уведомления

Порядок обработки: лимит по IP → проверка honeypot и времени → валидация Zod → лимит по контакту → дедупликация → запись в базу → фоновые уведомления.

- Повторная отправка с тем же контактом и типом проекта в течение 10 минут возвращает существующую заявку и не создаёт дубль.
- Уведомления отправляются после ответа пользователю, поэтому сбой внешнего сервиса не влияет на сохранение.
- Результат каждой попытки (`sent`, `failed`, `skipped`) пишется в `NotificationLog`.
- Кнопка «Повторить» в карточке заявки сбрасывает статус и отправляет уведомления заново.

Telegram: создайте бота через `@BotFather`, отправьте ему сообщение и получите `chat_id` из `https://api.telegram.org/bot<TOKEN>/getUpdates`.

Почта: укажите SMTP-параметры. Заявки отправляются на адрес из `EMAIL_FROM`.

## Загрузка изображений

Обложки сохраняются в `public/uploads/projects` с именем UUID и расширением из проверенной сигнатуры файла (PNG, JPEG, WebP). SVG отклоняется. Размер ограничен 2 МБ. Файлы выдаются через `/uploads/projects/[file]` с `nosniff` и immutable-кэшем.

Это решение рассчитано на собственный сервер или VPS с постоянным диском. На serverless-платформах (Vercel) файловая система не сохраняет загрузки между запросами: подключите объектное хранилище (S3, R2, UploadThing) и вставляйте прямую ссылку в поле обложки. Поле ручного URL уже поддерживается.

## Production

### Vercel + Supabase: пошагово

Сборка на Vercel обращается к базе, потому что публичные страницы пререндерятся. Поэтому база и переменные окружения должны существовать **до** первого деплоя.

**1. Создайте проект в Supabase**

1. [supabase.com/dashboard](https://supabase.com/dashboard) → New project.
2. Задайте имя (`stacklab`), пароль базы (сохраните его) и ближайший регион.
3. Дождитесь окончания провижининга (~2 минуты).

**2. Возьмите две строки подключения**

Project Settings → Database → Connection string:

| Что взять | Порт | Куда | Переменная |
| --- | --- | --- | --- |
| Transaction pooler | 6543 | приложение на Vercel | `DATABASE_URL` |
| Session pooler (или Direct) | 5432 | только миграции | `DIRECT_URL` |

К `DATABASE_URL` допишите параметры, иначе Prisma упрётся в prepared statements PgBouncer:

```text
?pgbouncer=true&connection_limit=1
```

Итог выглядит так:

```text
DATABASE_URL=postgresql://postgres.abcdefghijklm:ПАРОЛЬ@aws-0-eu-central-1.pooler.supabase.com:6543/postgres?pgbouncer=true&connection_limit=1
DIRECT_URL=postgresql://postgres.abcdefghijklm:ПАРОЛЬ@aws-0-eu-central-1.pooler.supabase.com:5432/postgres
```

Пароль со спецсимволами нужно URL-кодировать (`@` → `%40`, `#` → `%23`).

Если у проекта есть только IPv6-адрес, «Direct connection» не откроется с машины без IPv6 — используйте **Session pooler**, он работает по IPv4.

**3. Примените миграции, заполните контент, создайте администратора**

Скопируйте шаблон и заполните его реальными значениями:

```powershell
copy .env.supabase.example .env.supabase
```

`.env.supabase` в `.gitignore`, поэтому секреты не попадут в репозиторий. Проверка без подключения к базе:

```powershell
npm run db:supabase -- --check
```

Применение схемы, демо-контента и создание администратора:

```powershell
npm run db:supabase
```

Скрипт валидирует строки подключения (порт 6543 для пулера, 5432 для миграций, `pgbouncer=true`), затем вызывает миграции, seed и `admin:create`. Флаги: `--skip-seed`, `--skip-admin`.

Вместо файла можно задать те же переменные в оболочке (`$env:DATABASE_URL="..."` и т.д.) и выполнить `npm run db:setup` + `npm run admin:create`.

Скрипты увидят `postgresql://`, возьмут `prisma/postgres/schema.prisma` и применят миграцию через `DIRECT_URL`. Если `DIRECT_URL` не задан, миграция пойдёт через пулер и упадёт с ошибкой prepared statement — скрипт предупредит об этом заранее.

После этого Prisma Client сгенерирован под PostgreSQL. Чтобы вернуть локальную разработку на SQLite, выполните `npm run db:generate` (команда `npm run dev` делает это автоматически по текущему `.env`).

**4. Добавьте переменные в Vercel**

Project Settings → Environment Variables (Production и Preview):

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | transaction pooler, порт 6543, с `pgbouncer=true&connection_limit=1` |
| `DIRECT_URL` | session pooler, порт 5432 |
| `AUTH_SECRET` | тот же секрет, что использовали локально (минимум 32 символа) |
| `APP_URL` | `https://ваш-домен` (для превью можно `https://<project>.vercel.app`) |

Опционально: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `EMAIL_SERVER_*`, `EMAIL_FROM`. `ADMIN_EMAIL` и `ADMIN_PASSWORD` в Vercel не нужны — администратор уже создан в базе.

**5. Задеплойте**

`npm run build` сам генерирует Prisma Client под PostgreSQL (`scripts/prisma-target.mjs`), отдельная команда сборки не требуется. Если `DATABASE_URL` не задан, сборка остановится с понятным сообщением вместо каскада ошибок Prisma.

**6. Закройте таблицы от публичного API Supabase**

Prisma создаёт таблицы от имени `postgres`, поэтому RLS для него не действует, но Supabase по умолчанию отдаёт схему `public` через PostgREST. Включите RLS без политик — это заблокирует доступ через anon-ключ и ничего не сломает в приложении. SQL Editor → New query:

```sql
alter table "AdminUser"      enable row level security;
alter table "AdminSession"   enable row level security;
alter table "Lead"           enable row level security;
alter table "NotificationLog" enable row level security;
alter table "Project"        enable row level security;
alter table "Service"        enable row level security;
alter table "Testimonial"    enable row level security;
alter table "Faq"            enable row level security;
alter table "ProcessStep"    enable row level security;
alter table "SiteSetting"    enable row level security;
alter table "RateLimit"      enable row level security;
```

Дополнительно можно отключить API целиком: Project Settings → API → Exposed schemas.

**7. Проверьте**

- `/` и `/projects` открываются и показывают контент из базы;
- `/admin` редиректит на вход, вход работает;
- тестовая заявка сохраняется и видна в панели;
- письмо и сообщение в Telegram приходят, если каналы включены;
- экспорт CSV скачивается.

**8. Домен и HTTPS**

Добавьте домен в Vercel, обновите `APP_URL` и переdeployте: от него зависят canonical, sitemap и Open Graph.

**9. Обложки проектов**

На Vercel файловая система только для чтения, поэтому загрузка файлов вернёт понятную ошибку. Используйте поле «ссылка на обложку» с внешним URL (S3, R2, UploadThing, Cloudinary). Supabase Storage тоже подойдёт: бакет `public`, ссылка вида `https://<ref>.supabase.co/storage/v1/object/public/covers/file.webp`. Локально и на VPS загрузка работает.

### Особенности Supabase

- **Free tier засыпает** после ~7 дней без запросов. Первый запрос после паузы отвечает медленно; для боевого сайта лучше Pro или внешний пинг.
- **Лимит подключений.** Пулер нужен обязательно: каждый serverless-инстанс открывает своё соединение. `connection_limit=1` в `DATABASE_URL` держит это под контролем.
- **Прямое подключение только для миграций.** Не указывайте его в `DATABASE_URL` на Vercel: при нескольких инстансах закончатся слоты.
- **Бэкапы.** На Free daily backups недоступны — делайте `pg_dump` по расписанию (см. ниже).
- **Схема `public`** уже существует в новом проекте, `CREATE SCHEMA IF NOT EXISTS` в миграции это учитывает.

## Безопасность

- Пароли: scrypt с солью, сравнение через `timingSafeEqual`.
- Сессии: случайный токен, в базе хранится только SHA-256 хеш, срок 7 дней, отзыв при выходе и смене пароля.
- CSRF: токен в cookie и скрытом поле, сравнение на сервере.
- Лимиты: вход по IP и email, заявки по IP и контакту (фиксированное окно в БД).
- Все server actions и защищённые маршруты проверяют сессию на сервере, а не только скрывают интерфейс.
- Валидация всех входных данных через Zod, ограничение длины текста и размера запроса.
- IP посетителя хранится только как хеш с секретом.
- Загрузки: проверка сигнатуры файла, запрет SVG, UUID-имена, выдача с `X-Content-Type-Options: nosniff`.
- Заголовки безопасности и `noindex` для приватных разделов настраиваются в `next.config.ts` и `middleware.ts`.
- `robots.txt` не используется как механизм защиты: доступ закрыт авторизацией.

## Известные ограничения

- Публичные страницы кэшируются на 5 минут (ISR); после сохранения в панели кэш сбрасывается точечно.
- Восстановление пароля выполняется серверной командой `npm run admin:create`, отдельного email-сценария сброса нет.
- Локальные загрузки не предназначены для serverless-хостинга.
- Поиск по заявкам в панели чувствителен к регистру на PostgreSQL (`LIKE`). Для кириллицы это ожидаемо и локально: ищите по фрагменту в том же регистре или используйте фильтр по статусу.
- При изменении моделей миграции нужно создавать отдельно для SQLite и PostgreSQL (см. раздел «Две схемы»).
